# Static module source graph

`ProjectSources.unavailable` retains frozen `RejectedCall` ownership records for
recognized document calls that cannot resolve: module URI/version, call span,
known binding and causal diagnostics. No source, selector or schema facts are
invented. Failed initializer calls remain diagnostics only. Dependency failures
also retain ownership for previously resolved calls that become unavailable.

Module-wide traversal failure discards partial call records and keeps its module
diagnostic. Incremental results preserve cold ordering and can reuse unchanged
rejected records. These facts do not establish unavailable factory overloads,
artifact replacement or editor recovery; the generator still rejects errors.

`graphql_desk.source_graph.resolve_project(modules, bindings=())` consumes a tuple of caller-selected `ModuleSnapshot(project, module, uri, version, source, is_package=False)` facts. It never discovers files, imports project modules or executes Python. Module identity and URI must be unique within a project; project boundaries isolate identical module names.

The initial slice resolves stable module-level GraphQL Desk callable aliases, string constants, literal `+`, imports, relative imports, namespace access and transitive reexports. Each resolved call carries its source text, optional selected operation/binding, host call span, contributing literal spans and module URI/version dependencies. The cold function recomputes facts without a hidden global cache. Literal spans identify contributing expressions, not exact decoded-character mappings.

The resolver rejects ambiguous/rebound or mutation-dependent bindings and reports unsupported static-source cases at known GraphQL call sites. Ordinary imported Python functions and local lookalike modules do not become GraphQL candidates. Namespace reflection and escaped module objects may prevent a stability proof and must not yield successful precise facts.

This is a separate backend from the existing one-module `extract_calls` API, whose behavior remains unchanged. Direct ordinary/async function bodies now admit proven literals and stable module globals; unsupported scopes still receive conservative diagnostics. The shared source-map backend supplies exact decoded mappings, and fragment indexing/read-only editor consumers are integrated. Complete discovery, automatic precise import attachment and live generated inference remain open. Broad SRC-01 and live-typing gates remain open.

`ProjectBindings(project, schemas, default_schema=None, factories=())` supplies explicit project/schema facts; `FactoryBinding(module, export, schema_name=None)` identifies one exact imported callable. Export names are single Python identifiers. The resolver never guesses generated factories from a module prefix. Provided local template functions must remain stable and undecorated; missing, rebound or mutated supplied exports are rejected. External factory facts do not prove that an unprovided module exists or has a compatible runtime signature; static symbol integration remains separate work.

Root `init_graphql` calls resolve static schema strings/constants and preserve bound metadata through aliases and reexports. Configured facts reject unknown or ambiguous schemas; an unbound root/template factory uses only an explicit project default. Without project facts, runtime constructor syntax still yields unverified schema-name metadata. Diagnostic-only origin probes never assign schema metadata. `ResolvedCall.schema_name` is this schema identity; its separate `binding` field is the Python assignment name. No factory module or precise overload is generated by these facts.

Literal fragment argument lists/tuples resolve imported, reexported, qualified and inline document calls. `ResolvedCall.fragments` preserves caller order, including repeated references. Each `FragmentReference` carries an exact `DocumentIdentity(module, call_range)` target and the referring module/span; transitive dependencies retain actual URI/version facts. Source text is not concatenated. Static Python binding cycles, unresolved references and conflicting known schemas are diagnosed. GraphQL fragment definitions, spreads, type conditions and operation-as-fragment errors belong to #34, rather than these Python reference records.

Document resolution caches are local to one invocation and are populated only after mutation guards. Writes through document AST aliases, projections and literal containers invalidate affected origins; ordinary `client.execute(document)` or `document.ast` consumption is allowed. This finite analysis does not prove the behavior of arbitrary external Python code. Traversal failures discard affected dependent records instead of publishing dangling fragment targets.

`IncrementalResolver.resolve(modules, *, bindings=())` adds explicit in-memory
cross-request reuse. Serialize calls to one instance, including `clear()`.
Unchanged URI/source pairs reuse private parse/compile facts; every semantic run
constructs fresh mutable module state. A project reuses its complete result only
when its ordered full snapshots and binding facts match exactly. Source changes
with unchanged versions still invalidate it. Added, removed or reordered modules
and binding changes recompute that whole project; unrelated projects can reuse
their results. Whole-project invalidation deliberately covers failed exports,
missing package prefixes, shadowing and namespace-wide mutation reads that are
absent from successful dependency lists.

Complete request validation precedes reuse. New cache state replaces old state
only after success; removed inputs are evicted, no historical generations remain,
and `clear()` releases retained inputs/results. Calls and diagnostics preserve
cold resolver order, including parse errors preceding traversal diagnostics.
Chronology, cancellation and publication still belong to the caller's existing
freshness/ticket guard.

Eight cache tests compare cold and incremental results, count actual parse and
semantic work, and cover unchanged inputs, project/binding changes, negative
lookups, mutation/reexports, failure recovery, ordering and atomic cache updates.
This is incremental parsing and project-level semantic reuse, not module-level
semantic invalidation or a performance acceptance result. The bounded worker
serializes this resolver; schema/index caching and measured large-project
responsiveness remain open. Snapshot acquisition can retain exact
unchanged disk-source identities through an explicit previous-snapshot baseline;
local schema tokens still conservatively change on every acquisition.

`resolve_type_symbols(symbols, *, modules, project_id)` resolves configured type
exports against captured Python snapshots without importing or evaluating project
code. Immutable results distinguish supported captured class declarations,
uncaptured external symbols, unsupported forms, missing exports and known non-types.
Class aliases and package reexports reuse the existing source graph. Simple explicit
PEP613 aliases (`Alias: TypeAlias = ClassName`) also reuse those checks when the
marker resolves to uncaptured `typing.TypeAlias` or `typing_extensions.TypeAlias`.
On Python 3.12 and newer, non-generic PEP 695 aliases (`type Alias = Target`) use the
same bounded resolver; generic PEP 695 aliases remain unresolved.
Explicit `Annotated` aliases accept only `typing.Annotated` or
`typing_extensions.Annotated` with a named/qualified first type argument and at
least one metadata argument. Metadata is opaque and never resolved or evaluated;
the alias retains its own identity and cannot be used as a class base.
Direct `typing.NewType` and `typing_extensions.NewType` assignments with a literal
name and named class supertype resolve as non-base mapping types. Their call is
never executed; dynamic arguments and using a NewType as a class base stay
unresolved. Named or qualified type targets are supported. Unary collection aliases accept
one existing named/qualified type operand. Trusted constructors include `list`, `set`,
`frozenset`, `typing.List`, `typing.Set`, `typing.FrozenSet`, `typing.AbstractSet`,
`typing.Iterable`, `collections.abc.Iterable`, `typing.Collection`,
`collections.abc.Collection`, `typing.Sequence`, and `collections.abc.Sequence`.
Mutable counterparts include `typing.MutableSequence`,
`collections.abc.MutableSequence`, `typing.MutableSet`, and
`collections.abc.MutableSet`.
Variadic `tuple[N, ...]` retains its named/qualified element rule. Trusted `tuple` and `typing.Tuple` aliases also accept finite
nonempty fixed tuples of named/qualified types, preserving variadic behavior,
dependency/external propagation and valid class-base availability without element
TypedDict provenance. Empty shapes, inline/nested expressions and misplaced
ellipses remain unsupported. Mapping aliases support `dict[K, V]`, trusted `typing.Dict[K, V]`,
`typing.Mapping[K, V]`
and `collections.abc.Mapping[K, V]`, plus `typing.MutableMapping[K, V]` and
`collections.abc.MutableMapping[K, V]`, with exactly two existing named/qualified types.
They retain valid class-base availability and drop element TypedDict provenance;
either external operand keeps the alias unverified. Captured or mutated namespace
prefixes cannot establish a trusted external alias constructor. Supported builtin availability includes `bool`, while direct or
aliased `bool` class bases remain rejected as non-subclassable. Constructors must resolve to supported external `builtins`, `typing`,
`typing_extensions` or `collections.abc` exports; shadowing and mutations invalidate that proof. External arguments stay
unverified, and containers do not inherit TypedDict provenance from their element.
Explicit binary unions accept two direct named/qualified type operands or literal
None, with at least one named operand: `N | M`, `N | None` or `None | N`. Flat
`typing.Union[...]` and `typing_extensions.Union[...]` aliases use direct named
operands or literal None, and may appear inside a supported container alias.
Those operands may include a flat PEP 604 union, such as
`Union[str | int, None]` or `list[Union[str | int, None]]`; its leaves follow
the same direct-name rule.
Trusted external `typing.Optional[N]` retains its one named/qualified operand.
Aliases retain their own identity and never confer class-base or TypedDict
capabilities through aliases or reexports. External operands remain unverified.
Duplicate union operands also retain the conservative non-base policy: runtime
and Pyright allow the tested reduced class base, while pinned mypy rejects it.
Nested PEP 604 union groups, nested Union arguments, and general recursive Union
evaluation remain unsupported.
Trusted external `typing.Literal` and `typing_extensions.Literal` aliases accept
one or more flat string, bytes, integer, boolean or None constants, plus one unary
minus on an exact integer. They retain their own identity without class-base or
TypedDict capability. Named values, enum-member expressions, floating/complex
constants, empty arguments and nested expressions remain unsupported. Captured
preflight rejects Literal-based subclasses; the pinned Pyright accepts the tested
invalid subclass, while mypy and runtime reject it. Mapping value negatives pass
both checkers.
Shadowed markers, ordinary marker value assignments, ordinary variable annotations,
string forward targets, nested subscriptions, other union forms,
custom generic
constructors,
cycles and mutations remain unresolved. Dependencies retain the entire captured
project, including negative lookups.

Captured ordinary classes may use trusted external `dataclasses.dataclass` and
`typing.final`, including aliases/reexports and one of each in either order.
Captured enum classes may use bare trusted `enum.unique`, including import
aliases. Its call is not executed during analysis.
Dataclass calls accept only literal boolean `frozen`/`slots` options, with no
positional or unpacked arguments. Dataclass-decorated declarations require no
bases or trusted `object`; inherited decoration remains unsupported because
frozen and non-frozen combinations can fail at runtime. Ordinary undecorated
subclasses of supported dataclasses retain existing base checks. Final classes
remain valid mapping values but cannot establish class bases through aliases or
reexports: both strict checkers reject the tested subclass although runtime permits
it. Decorated TypedDict classes and enum classes with decorators other than
`enum.unique` remain unsupported, including inherited and reexported special
bases. Supplied or mutated decorator namespaces, writes to
decorator functions and recognized capability escapes cannot establish trust.
No decorators execute during analysis.

Other decorators, unsupported class keywords/bases, richer annotated aliases and
dynamic type factories remain unresolved. Recognized namespace escapes invalidate affected
facts; `sys.modules` reflection and captured `__builtins__` access or replacement
conservatively prevent project type resolution. This type-only guard preserves
ordinary document/parser facts and isolates other projects.
The selected-interpreter capture reads bounded external `.pyi`/`.py` declarations
for configured mapping symbols and imported class bases used by captured project
classes. Captured class declarations and reexports can establish a mapped local
subclass without importing or executing package code. Missing, ambiguous,
oversized, binary-only and unsupported namespace-only sources remain unverified.
This proves static symbol availability, not runtime identity or full checker
compatibility. Factory mapping preflight consumes these facts before emitting
artifacts; the broader editor/doctor integration and type compatibility matrix
remain open.

Captured TypedDict subclasses retain trusted base provenance through name and
qualified aliases, explicit supported TypeAlias targets and reexports. This permits
inherited `total=True`/`total=False` declarations while rejecting mixed ordinary
class bases, shadowed markers, mutations and unsupported metaclass semantics.
Inherited-only `closed` remains unresolved; the existing direct-marker policy is
unchanged. Actual-source mapping fixtures pass both strict checkers and runtime
checks without importing project modules during generation. Full Python type
compatibility and external-symbol verification remain open.

Direct module-level ordinary and async function bodies use whole-function local
binding checks before resolving callable, source, fragment or operation inputs.
Parameters, local imports/assignments, exception and pattern bindings, and named
expressions cannot silently select a same-named module global. Rebound or later
initial globals remain unresolved. Function calls keep their original owner/span
and may have no export binding; existing inline artifact generation handles them.
Unrelated directives inside nested helper scopes no longer disable proven outer
calls; projectwide blocked-name checks still reject relevant global mutations.

Functions with inline type parameters, closures/nested functions, classes, lambdas, comprehensions,
calls inside default/decorator/annotation expressions and direct outer-body
global/nonlocal declarations remain outside
this bounded subset. Actual function/async source fixtures exercise both strict
checkers and runtime identity. This does not complete static-source or live typing
acceptance or authorize any generated-file publication.
