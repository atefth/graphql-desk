# Managed live typing artifacts

GraphQL Desk uses the existing analysis worker to produce the multi-file `.pyi`
tree that Pylance needs. In a trusted file workspace, the extension publishes
those artifacts under the Pylance stub root in a namespaced package. If no
`python.analysis.stubPath` value is explicitly configured, it reserves
`.graphql-desk/typings` but leaves the setting alone until a complete generation
is ready; then it points the setting at that immutable generation. This is the
user-approved ownership policy. An explicit blank value is preserved and uses
Pylance's `./typings` default; a workspace-local custom root is reused, including
changes made while the extension is running. Workspace-setting-only management
refuses an external root; project-config management preserves access to a prior
external custom root while publishing inside the owning workspace.
Existing settings and files outside GraphQL Desk's owned package are preserved.

When a project has `pyrightconfig.json`, GraphQL Desk uses it ahead of
`[tool.pyright]` in `pyproject.toml`, matching Pyright's configuration
precedence. Under the approved managed-config policy, it selects completed
generations through the effective project's `stubPath`, preserves the prior
value for restoration, and retains access to the prior custom stub root and
existing `extraPaths`, including execution-environment overrides. This supersedes
the earlier extraPaths-only implementation in #330. JSONC comments and unrelated
settings are retained; TOML is edited with `tomlkit`. Ownership records distinguish
the entries GraphQL Desk created from existing configuration, so cleanup restores
the user's prior values without removing unrelated entries. Native configuration
reload consumes the completed selection; managed project-config publication does
not request an extra initial language-server restart.
Malformed, dirty, symbolic-link, ambiguous or concurrently changed configs are
left untouched and live typing fails closed. Generated `.pyi` updates use a
clean VS Code document edit and save; a dirty or racing document is preserved.

The output manager accepts only safe `.pyi` paths beneath the worker's configured
generated package. It creates only new package files and directories, rejects
foreign collisions, symbolic links and dirty aliases, and verifies ownership,
freshness and bytes before each replacement. Updates are serialized and staged;
failed replacement rolls back only bytes still owned by this process. Removed
outputs and shutdown cleanup remove only matching owned files and empty owned
directories. Source invalidation and analysis failures quarantine affected
operation types until current analysis succeeds; unrelated valid declarations
are retained where their provenance permits. A retained generation is recovery
material, not evidence that stale precise types are safe to expose. In the
workspace-setting-only path, an existing custom root outside the workspace is
left untouched and surfaced as managed typing unavailable.

Each generated `.py` and `.pyi` has a deterministic content fingerprint in its
header, based on its package-relative path, body and writer format. Initial
creation stages every artifact before exposing any final path. This fingerprint
does not include source, configuration or schema facts and is not a durable
manifest.

The managed-generation manifest also records a separate input fingerprint over
captured Python source contents, schema contents and non-secret configuration
semantics. Remote URLs and headers are excluded; the loaded schema content is
included. The manifest's artifact fingerprint continues to verify the published
bytes. The worker also captures a separate saved-source fingerprint from backing
Python files, including disk contents under dirty editor overlays. Freshness
checks recapture those backing files before publication. The live input
fingerprint continues to include current overlays; the two values identify
distinct snapshots without serializing credentials.

When GraphQL Desk owns the previously unset setting, generated bytes are staged
as an immutable generation and `python.analysis.stubPath` is rotated to select
it; Pylance reloads the typing tree from that setting change without an explicit
server restart. For an explicitly configured workspace-local root, the extension
retains the protected in-place writer and restarts Python analysis after changes.
The focused Windows host fixture uses the real
worker and pinned Python 2026.10.0 / Pylance 2026.4.1 in VS Code 1.141.0 and
1.142.0. It observes result type `GraphqlDeskResult`, selected field `String`,
variable `Int`, rejection of a string variable, and a schema nullability edit
changing Pylance hover to `String | None` with an invalid-assignment diagnostic.
Changing the workspace stub root at runtime also moves the owned package. Host
shutdown removes the GraphQL Desk package while preserving a neighboring user
file and workspace settings.

Native tests cover path/settings precedence, empty-output cleanup, exclusive
creation, stale work, serialization, links/path changes, foreign bytes/inodes,
dirty aliases, partial initialization, rollback and teardown ordering. These
results prove only this narrow generated-artifact bridge. They do not establish
restart recovery after a crash, cross-process compare-and-swap, multi-workspace
conflict handling, performance under edit storms, or the broad full-parity gate.

## Lifecycle ownership and recovery limits

The multi-file writer checks dirty file and associated untitled buffers before
initial creation and before adding a new destination. It rechecks staged files,
destination buffers, workspace trust and directory identity before replacement,
rollback and cleanup. If ownership changes during a failed update, preserving
the user's buffer or foreign path takes priority over restoring the previous
bytes. That conflict can leave owned or staged files in place and makes managed
typing unavailable; cleanup does not force saves, revert buffers or delete the
unverified files. A completed write shortened externally before a sync failure
is also preserved rather than mistaken for the writer's own partial write.

Source inventory starts with the current disk enumeration, adding dirty or
untitled Python buffers. A clean document retained by VS Code after its backing
file is renamed or deleted does not resurrect that source or its obsolete
generated companion. The retained document and user buffers are not edited by
this inventory change.

### Removed workspace folder (#23 / #24)

Removing an owning workspace folder now allows terminal cleanup of that
session's verified artifacts even though VS Code no longer reports an owner.
Publication still requires the original owner. Cleanup still rejects a new
owner, lost trust, changed directory or file identities, foreign bytes, and
dirty generated buffers; it never saves or reverts a document.
A cleanup request immediately blocks new publications, but ownerless verification
is permitted only inside the serialized cleanup action, never an in-flight publish.

The focused `workspaceRemoval` host suite starts with an explicit two-folder
workspace and removes the second folder through VS Code's public API. It checks
that only its owned package disappears, its unsaved Python buffer retains its
text/version/dirty state and saved disk bytes, a neighboring user file survives,
and the remaining workspace retains Pylance's `String` hover. Run it with
`npm run test:host -- 1.142.0 workspaceRemoval` (or `1.141.0`). Native editor
checks now pass 97/97, including detached cleanup conflicts and a cleanup request
made during publication's current-source check. This evidence is
bounded to session-owned cleanup; restart recovery and the broad gates remain
open. Both pinned Windows hosts passed with Python 2026.10.0 / Pylance 2026.4.1;
selected results are in `editor/test/observations/workspace-removal-*.json`.
The unchanged `factoryArtifacts` suite also passed on 1.142.0 without tracing.
Earlier runs timed out before initial publication; their precise cause remains
unresolved. Startup reliability was not fixed or established by this cleanup
change. The removal fixture uses a preconfigured
stub root and starts in a two-folder workspace so no single-to-multi-folder
transition or unsaved-workspace prompt is needed.

### Managed project-config security (#356)

Project-config replacement uses the same native permission checks as `init`.
The trusted worker receives an explicit real workspace anchor; ordinary workers
remain read-only. It captures the original file's bytes, identity and security
metadata, rejects malformed UTF-8, then creates an empty sibling and establishes
equivalent permissions before writing any config content. Unknown permissions,
redirected paths or changed ownership fail closed. Config text and native access
descriptors are not included in recovery records or diagnostics.

The editor journals intent before staging and persists the worker's opaque
receipt before publication. Native verification is the last awaited operation
before synchronous trust, dirty-buffer, path, identity and content checks and
rename. Every bounded Windows lock retry requires fresh native verification.
Python and Node file identities are never compared across runtimes. These
guards narrow replacement races; they are not a universal filesystem
compare-and-swap guarantee.

An interrupted write keeps its recovery journal until native finish or discard
verifies the exact owned file. A resumed receipt authorizes recovery only, never
publication. Legacy or incomplete records without a complete security proof
require explicit recovery; matching hashes alone cannot authorize deletion or
restaging. Changed or foreign files remain untouched. An incomplete stage blocks
further staging across worker restarts instead of accumulating another temporary
file on every retry.

Staged-file cleanup also uses a read-only native verification followed by the
editor's final synchronous dirty-buffer, trust, directory, identity and byte
checks before unlink. Python only confirms the resulting absence. The journal
records cleanup intent first, so recovery distinguishes an interrupted discard
from a completed config replacement. Opening a dirty staging buffer while the
native check is pending preserves the file instead of racing an asynchronous
Python deletion.

For a legacy or incomplete record, run **GraphQL Desk: Review Interrupted Config
Write**. Inspect the config and reserved temporary paths shown in its dialog
before confirming. This forgets only the unchanged pending record and resets the
old worker; it preserves every file. Review or retain any uncertain temporary
file yourself. Cancellation, workspace changes and a changed record leave the
record intact. A new update still has to pass ordinary native permission,
ownership and currentness checks; acknowledgement does not approve those files
for overwrite or deletion.

Backend and transport fixtures cover these boundaries; complete installed-editor
and platform verification is tracked by #356. This does not resolve reader-safe
generation retirement under #355 or pass broad TYPE-01 acceptance.

Local verification for this change passed 106 backend tests (four existing POSIX

VS Code 1.141.0 exercised the TOML lifecycle and 1.142.0 the JSONC lifecycle,

### Immutable generations and recovery (#37 acceptance complete)

When GraphQL Desk owns the previously unset stubPath, it now stages each analysis
under a unique generation directory. A manifest containing the generated file
hashes is written last; only a generation whose complete manifest and files
verify can be selected. Pylance's stubPath is the generation selector. The
extension also records each generation ID and manifest fingerprint in its
workspace state. A valid-looking directory or manifest without that ownership
record is never adopted, selected, or deleted. Publication and recovery are
serialized so overlapping analyses cannot give stale output the newest
generation order. The workspace setting is rotated only while its value still
matches the extension's persisted ownership record; a user change causes
GraphQL Desk to stop managing that setting. The manifest and artifact hashes
are checked again after ownership persistence and immediately before the
setting switch. Explicit user-configured stub roots are never rotated and
continue to use the protected in-place writer.

On activation, the extension scans for complete, unmodified generations and
selects the newest valid one. Incomplete, dirty, changed, extra-file, or
symlink-containing generations are left untouched. It retains the newest two
verified generations and removes an older generation only when every byte,
file identity, directory, and buffer still proves GraphQL Desk owns it. These
ownership checks do not establish that Pylance has finished reading the old
directory. Hosted evidence of Pylance indexing a deleted generation is tracked
by [#355](https://github.com/atefth/graphql-desk/issues/355); safe reader lifetime
and bounded storage remain required, unresolved acceptance. The selection and
restart follow-ups remain under #329 and #351. A crash
before manifest commit leaves the previously selected generation usable; activation
can recover it. Pylance-visible settings writes are excluded from the broad source
watcher, and GraphQL Desk's own `settings.json` text-document events are ignored;
Python and GraphQL Desk configuration events and all unrelated watched files still
invalidate analysis. The real VS Code/Pylance fixture verifies an unsaved
cross-file fragment edit updates hover and diagnostics, then leaves the retained
generation count unchanged after convergence without an explicit restart. The
native tests also cover forged generation directories, rejected state writes,
mutation during ownership persistence, and stale overlapping publication. Each
complete generation now includes all returned runtime `.py` companions alongside
its `.pyi` files. Every runtime path must have a same-generation stub with the
same module path; stub-only modules remain valid. Both file kinds are hashed and
verified by the completion manifest before selection. The implementation
acceptance for #37 is complete through #212 and linked #207/#210. This does not
pass broad live typing TYPE-01: broader invalid-edit recovery,
cancellation races, forced-crash recovery, and the full editor lifecycle matrix
remain part of broader TYPE-01 acceptance and the open #329/#355 follow-ups.
The bounded #38 story is closed; it is not a broad gate pass. This change does
not adopt pre-existing packages or authorize deletion of user files.

The `restartRecovery` host suite now launches two separate VS Code processes
against the same isolated workspace and profile. After the first process
publishes a complete generation and exits, the second reopens the saved Python
consumer and confirms the same generation is selected, Pylance hover reports
`selected: String`, and the invalid variable diagnostic returns. This passed
on Windows VS Code 1.141.0 and 1.142.0 with Python 2026.10.0 and Pylance
2026.4.1; results are in
[`restart-recovery-1.141.0.json`](../../editor/test/observations/restart-recovery-1.141.0.json)
and [`restart-recovery-1.142.0.json`](../../editor/test/observations/restart-recovery-1.142.0.json).
This verifies a normal application restart with a valid completed generation.
It does not simulate a forced process crash during a write, and it does not
establish the broader live-typing lifecycle gate on its own. The bounded #24
story is closed; its completion is separate from full TYPE-01 acceptance.

### Issue #38 cancellation and invalid-operation recovery

The editor refresh generation now passes its cancellation token into artifact
generation. Source/configuration invalidation, caller cancellation, and
controller disposal abort active worker requests; a result arriving after any
of those transitions is rejected before publication. Native controller tests
cover each transition and a subsequent fresh generation. The pinned VS Code
1.142.0/Pylance 2026.4.1 host check edits one of two operations in a Python
module to reference an unknown field: the affected artifact becomes
`GraphqlDeskUnavailable`, Pylance reports an unknown result type, and GraphQL
Desk reports the validation diagnostic, while the unaffected operation keeps
its `ID` hover. Repair restores the affected `String` hover and removes the
diagnostic. See
[`issue-38-invalidation-1.142.0.json`](../../editor/test/observations/issue-38-invalidation-1.142.0.json).
The same pinned host also observed schema and scalar-config invalidation and
repair, plus switching the worker interpreter from Python 3.10.0 to 3.12.1
and restoring it. The selected hover changed from `Boolean` to `String`, and
the test records actual worker requests after each setting change; an
independent operation retained its `ID` hover.
See
[`issue-38-invalidation-repair-interpreter-1.142.0.json`](../../editor/test/observations/issue-38-invalidation-repair-interpreter-1.142.0.json).
This does not test delayed/superseded publication or prove the full lifecycle
matrix.
This is bounded evidence only; hosted Stage 1 gate #42 passed, while broad TYPE-01 acceptance remains open.
