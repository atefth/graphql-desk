## Measurable responsiveness contract

No upstream numerical SLA was established; these are GraphQL Desk planning budgets chosen to make “responsive” testable. They do not weaken any semantic feature requirement.

- Reference runner: dedicated 4 vCPU, 8 GiB RAM, SSD, no competing benchmark jobs; record exact machine/OS/runtime versions. Each platform runs a correctness/latency smoke check; full benchmark runs on the Ubuntu reference runner. Repeat five cold processes and 100 edits after warmup; publish p50/p95 and max, use monotonic timestamps.
- Small workspace: 100 Python modules, 100 operations, 50 fragments, one 500-type schema. Large workspace: 2,000 modules, 2,000 operations, 1,000 fragments (acyclic chains depth 10), two 2,000-type schemas; average operation 2 KiB; Unicode/CRLF variants. Fixed generator seed 1; retain fixture manifest and counts in eventual benchmarks.
- Debounce 100 ms; from last unsaved edit to version-current GraphQL diagnostics, p95 <=300 ms small / <=750 ms large. Completion/hover response p95 <=150/300 ms. From edit to dependent Pylance hover plus Python diagnostic refresh p95 <=1/2 seconds. Individual large request timeout 5 seconds produces a visible pending/failure state, never a false current result.
- Cold index plus initial types <=3/10 seconds small/large; combined GraphQL Desk Python/Node worker resident memory <=256/768 MiB (measure Pylance separately). Idle work <=1% of one core averaged over 60 seconds after settling; no linear memory growth over 1,000 edits/close/reopen cycles (<=10% post-GC delta).
- Correctness always wins: every timing sample must identify source/schema/config versions; old-version results never count as successes. Schema change invalidates only affected schemas; fragment change only dependents. No persistent cache is required. If added, compare complete output/diagnostics with cache off and exercise every invalidation key before accepting its timing advantage.

These thresholds can be tightened or revised using recorded benchmark evidence and a reviewed decision; they cannot be silently relaxed to claim parity.

## Classification of previously unchecked work

The planning goal is a complete, reproducible capability/requirements contract before Python implementation. It does not require a Python product test to pass before that product exists. The distinctions below are deliberate; missing upstream behavior discovery would still block planning.

| Previously unchecked item | Classification and reason | Required follow-up |
|---|---|---|
| Upstream test-suite rerun | Not an unfinished inventory/specification gap: relevant pinned tests and source define the expected cases, quirks and maturity, and the Python contracts specify their equivalents. Running upstream TypeScript tests checks the reference environment; it cannot prove the future Python outcomes. | During the first implementation test-infrastructure slice, run relevant pinned upstream reference fixtures and encode Python differential fixtures; full reference-suite execution before a full-parity release claim. If results contradict inspected source, reopen the contract. Do not report suites as passed now. |
| Narrow spike reruns | Not a remaining scope decision: reports/tool versions/input/action/expected-output recipes are preserved, and every broad typing/lifecycle case remains an explicit gate. A repeat of one nullability/identity example cannot close those gates. | Reproduce the narrow baselines in isolated extension/checker fixtures when implementing the live-typing foundation, then broaden semantics/lifecycle before exiting that gate. | Published/source capability correspondence | Was research needed for planning; now extended beyond export names using tarball source maps and recorded differences below. Unexamined artifact behavior could otherwise silently change the target. | Preserve the published/pinned-source distinction in reference fixtures. |
| Complete reproducible build / byte-for-byte equivalence | Documented verification limitation, not a missing product requirement. ### Additional published-source audit actually completed

On 2026-10-19 fetched and integrity-verified the root tarballs again plus exact runtime dependencies `@gql.tada/cli-utils@1.9.4` and `@gql.tada/internal@1.2.2` named by published gql.tada 1.11.4. Read each `.mjs.map` `sourcesContent`, excluding third-party `node_modules` entries; matched local-source paths to pinned Git objects and compared text after CRLF→LF normalization. This is a direct text comparison of embedded originals, not execution or reproducible-build proof.

- gql.tada embedded originals match the pin: `src/api.ts`, `src/utils.ts`, `src/testing.ts`, `src/cli/index.ts`. This covers runtime document/scalar/fragment helpers and CLI dispatch, not every erased type declaration.
- cli-utils embedded originals compared equal: commands/check/schema/output/persisted/turbo/init/doctor/scan, shared project/diagnostic/terminal/CI support, scan graph/context/rules/output modules and worker sources represented in the maps. All eight scan rule sources and persisted collector/writer agree with the pinned source used by the contract.
- internal embedded originals compared equal: loaders/introspection/schema URL/SDL, errors, config/resolve and emitted introspection minify/preprocess/output sources represented in the maps.
- GraphQLSP: 14 embedded local source files match; four differ: `ast/index.ts`, `graphql/getSchema.ts`, `index.ts`, `quickInfo.ts`. Inspected all four diffs. `ast/index` adds an exported resolver in the pin; schema output adds unique swap-file handling; plugin entry adds config routing/duplicate-instance protection, quick fixes, fragment extraction and references/rename; quickInfo adds structured signatures/defaults/descriptions/deprecation. Published 1.17.5 lacks those newer source additions despite the same manifest version. Persisted hashing, diagnostics, field use, imports and relevant discovery sources represented in both maps match.

Its 1.17.5 manifest is metadata, not proof that npm 1.17.5 ships the source additions. Keep every already-required editor convenience and highlighting capability; do not downgrade to the smaller published plugin. This clarifies the existing broader source target without dropping features or requiring a new user choice. Acceptance fixtures must label published behavior versus source-only additions.
