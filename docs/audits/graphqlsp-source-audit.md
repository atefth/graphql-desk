**Purpose:** source-level inventory of the editor experience gql.tada delegates to GraphQLSP, with reuse boundaries for a Python/Pyright/Pylance implementation.

## Verified editor-visible feature inventory

GraphQLSP is a **TypeScript language-service plugin**, not a standalone GraphQL LSP server. It wraps a TypeScript `LanguageService`, augments selected methods, and uses the TypeScript project/type checker to find GraphQL expressions and import relationships. The public feature list and source/tests together establish these behaviors:

GraphQL validation comes from `graphql-language-service`; TypeScript node/source positions and diagnostic conversion are GraphQLSP glue. | Reuse GraphiQL's validator/rules and GraphQL AST validation in Python. ## What GraphiQL language-service OSS can and cannot supply

GraphQLSP's manifest directly depends on `graphql-language-service` and `graphql`, alongside `@0no-co/graphql.web`, `@gql.tada/internal`, TypeScript, and small utilities. Its completion, token parsing, type-info/hover and schema diagnostics call GraphiQL's language-service functions. This is a strong reuse candidate for GraphQL semantics if a compatible Python API/package version is selected; the local GraphQL Desk spike already used the lower-level package behind an LSP adapter.

GraphiQL language-service does **not** provide the gql.tada-specific TypeScript AST extraction, fragment dependency resolution through TypeScript imports/arrays, fragment reference/rename workspace index, TypeScript result-property tracking, persisted-call/hash validation, schema output writing, or gql.tada refactors. It is also not a drop-in Python library: a Node-backed process, language-service package, or a Python-native GraphQL parser/validator plus matching completion logic must be selected deliberately. Existing source audit evidence for GraphQL Desk's `graphql-language-service` slice remains valid for core schema features only.

Other reusable OSS foundation: `graphql-core` can provide Python GraphQL parsing, schema types, AST/source locations and spec validation. Pyright/Pylance can provide Python type checking and `.pyi` consumption. Neither supplies the Python source-to-GraphQL project index, operation result/variable type renderer, fragment-use graph, or live `.pyi` document refresh lifecycle. Generic LSP has standard diagnostics, completion, hover, definition, references, rename, code action, code lens and document-symbol methods; each must be implemented and source-mapped. The TypeScript plugin APIs GraphQLSP overrides (`getSemanticDiagnostics`, `getCompletionsAtPosition`, `getQuickInfoAtPosition`, definition/reference/rename methods, `getCodeFixesAtPosition`, `getApplicableRefactors`, `getEditsForRefactor`) are not themselves LSP endpoints.

## Assumptions and gaps to reconcile in existing planning

1. **Don't collapse gql.tada core typing into GraphQLSP.** GraphQLSP supplies editing feedback around extracted documents. gql.tada's operation result and variable inference comes principally from gql.tada's TypeScript type-level machinery. GraphQL Desk's generated schema typings and live operation `.pyi` generation are required parity work and remain separate.
2. **Don't claim GraphiQL service covers the whole editor surface.** It is a good diagnostics/completion/hover engine. References/rename, safe edits, extraction, import/field-use diagnostics, persisted IDs, outline and type updates need independent implementation and acceptance tests.
3. **Keep the limits on heuristics.** `trackFieldUsage` is same-file and client-preset/call-expression-specific, excludes mutations/subscriptions, and may false-positive. It is not equivalent to schema-wide reachability/project scan. Preserve the distinction in the existing `scan-performance-types-review (prior local memo)`.
4. **Treat generic LSP and VS Code as separate layers.** Core LSP behavior should be editor-neutral. Outline/syntax highlighting, command menus and Pylance integration require client-specific contributions. GraphQLSP's refactors are TS language-service extension points, so translate them to LSP code actions; don't expect a plain GraphiQL LSP package to surface them.
5. **Scope persisted IDs as a feature, not a default hash shortcut.** The source resolves fragment closure and gql.tada-specific directives before hashing. A raw hash of the visible operation text will not be compatible. The persisted document editor action is verified upstream but Python API/manifest parity is still open.
6. **Multi-schema and schema output exist upstream.** Config supports named schemas, schema selection tied to gql.tada call typing, schema watchers, and per-schema introspection output. Prior local support matrices already mark GraphQL Desk multi-schema unproven; retain that gap but include named-schema selection and independent refresh/output in acceptance.
7. **Generated schema typing is not generated operation typing.** `tadaOutputLocation` writes an introspection representation. Existing Pylance bridge proof (nullable field only) is still the only local live operation-type evidence; broad result/variable semantics, error recovery and lifecycle remain open.
8. **Some features belong to `@0no-co/graphqlsp` packaging or VS Code extensions.** README's Outline claim is extension-level. The GraphQLSP source repository has an `packages/vscode-graphqlsp` package; do not attribute extension UI features to the language-service plugin alone.
9. **Dependency/API boundary needs a pinned decision.** `graphql-language-service` is JavaScript/TypeScript OSS, not Python-native. Prior dependency audit may still rule out promoting the exact GraphiQL CLI/server tree; this audit only supports reuse of the lower-level language-service APIs or behavior, subject to a production dependency review.

## Acceptance criteria for GraphQL Desk's gql.tada-like editor surface

At minimum, maintain automated fixtures that run in a real VS Code extension host with the target Pyright/Pylance path active, plus protocol tests independent of VS Code:

- A GraphQL edit in every supported source form produces correctly mapped schema diagnostics, completions, hover and schema/fragment definitions; invalid/incomplete text recovers; another schema/document edit clears stale diagnostics and types.
- Python files can navigate fragment definitions/spreads and references; renaming a fragment edits only symbol references in the indexed workspace, including cross-file references, and preserves unrelated same-spelled strings/comments.
- Code actions cover misspelled field replacement, deprecated-field replacement only where a replacement is known, safe unused-field removal, and extract-to-fragment with correct placement and all required imports. Refuse edits that would make invalid/empty selection sets.
- Colocation analysis resolves Python exports/imports and warns only when an imported fragment is not composed into a document under the documented rules. Field-use warnings separately document same-file limitations, reserved keys, supported access patterns, false positives, and mutation/subscription policy.
- Multi-schema config selects the intended schema for each operation, diagnoses unknown names and load failures, watches edits to each schema, and refreshes only affected operations/output. URL auth, secret redaction and schema/output write errors have tests.
- Persisted operation checks use a documented canonicalization/fragment closure and stable supported hash; nested fragments, gql.tada-only directives, stale IDs and missing IDs have fixtures. The code action yields an exact deterministic replacement.
- Required schema typings and live operation result/variable types update Pyright/Pylance without manual generation after unsaved GraphQL edits. Test aliases, list/item nullability, variables/defaults, enums/inputs, unions/interfaces, fragments/masking, directives, scalars, invalid edit recovery, close/reopen, multiple operations, cancellation and stale-result prevention. Cache remains optional.
- Outline/document symbols expose operation and fragment names. Embedded Python GraphQL syntax highlighting is required as the equivalent of the pinned VS Code extension grammar contribution; it remains separate from semantic diagnostics and type inference.
- Every feature has parity tests at the observable protocol/UI boundary, not only parser unit tests. Record unsupported Python syntax/access patterns and clear diagnostics instead of silently returning stale or falsely precise information.

## Final planning audit correction

The pinned [VS Code extension manifest](https://github.com/0no-co/GraphQLSP/blob/5f277f3fd444af4e7175c3e9afefd73cad465b5d/packages/vscode-graphqlsp/package.json) and [activation source](https://github.com/0no-co/GraphQLSP/blob/5f277f3fd444af4e7175c3e9afefd73cad465b5d/packages/vscode-graphqlsp/src/extension.ts) were inspected directly on 2026-10-19. The earlier plugin-only README interpretation missed extension highlighting. The extension also forwards schema(s), custom template, call-expression mode, colocation/field-use, client-directive and output/preprocessing settings, gives project configuration precedence, and requests server restart on setting changes. Python equivalents need documented configuration precedence and application/reload behavior. The manifest is private version 0.1.0; this is source evidence, not proof of a published Marketplace package.

The plugin also exports an [API subpath](https://github.com/0no-co/GraphQLSP/blob/5f277f3fd444af4e7175c3e9afefd73cad465b5d/packages/graphqlsp/src/api.ts): diagnostics, initialization, call/persisted discovery, fragment unrolling and document-reference helpers. Their Python capability disposition belongs to API-01, with TypeScript implementation mechanisms mapped explicitly rather than promised literally.
